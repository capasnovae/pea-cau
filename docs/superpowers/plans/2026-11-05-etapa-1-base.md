# PEA · Etapa 1 (Base) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dejar andando la base de PEA: app Next.js mobile-first con login por invitación, roles, puestos y subroles, sedes y equipos, el esquema de organización con RLS probada, y la administración mínima de usuarios.

**Architecture:** Next.js (App Router) habla con Supabase usando `@supabase/ssr`. Toda la autorización vive en Postgres: funciones auxiliares (`mi_rol`, `mi_sede`, `mi_area`, `puede_ver_usuario`) y políticas RLS, probadas con pgTAP. La UI solo oculta lo que no corresponde. Se desarrolla contra el stack local de Supabase (Docker). **No se crea infraestructura remota** hasta que el usuario pase las cuentas nuevas.

**Tech Stack:** Next.js 16 (última estable; la spec decía 15, se usa la vigente), TypeScript estricto, Tailwind CSS 4, shadcn/ui, `@supabase/ssr`, `@supabase/supabase-js`, Supabase CLI (Postgres 17 local), pgTAP, Vitest, Playwright, ESLint, Prettier, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-05-pea-design.md` (fuente de verdad: https://claude.ai/artifact/X1q2HM1snEgLHYWUJWebwP)

## Global Constraints

- UI en español rioplatense (voseo: "Ingresá", "Revisá tu email"). Mobile-first: todo se diseña primero a 360 px de ancho.
- Nombres de tablas, columnas y funciones SQL en español y en snake_case. Claves primarias `uuid default gen_random_uuid()`. `created_at timestamptz not null default now()` en todas las tablas y `updated_at` por trigger donde se edita.
- Funciones auxiliares de RLS: `security definer`, `stable`, `set search_path = ''`.
- La service role key se usa **solo** en el servidor (Server Actions / Route Handlers), nunca en el cliente.
- El usuario no puede modificar su propio `rol`, `sede_id`, `area`, `equipo_id` ni `puesto_id`. Solo el admin cambia `rol`.
- Login: email y contraseña, alta solo por invitación del admin. No hay registro abierto.
- Sedes iniciales (seed): Neuquén, Plottier, Zapala, Cipolletti, Bariloche, Cutral Co, Roca.
- Director: alcance sobre todos los CAU. Coordinador: su sede y su área. Líder: su equipo.
- No se guardan datos de alumnos.
- No usar ningún proyecto remoto de Supabase existente (en particular, no tocar `amapola-tienda`).

## Review Focus

1. **Autoescalada de privilegios:** un asesor hace `update perfiles set rol='admin' where id=auth.uid()` desde el cliente → debe fallar. (Test en Task 4.)
2. **Usuario desactivado (`activo=false`) con sesión vigente:** no debe ver datos de nadie más que de sí mismo y la app lo saca a `/ingresar?motivo=inactivo`. (Tests en Task 3 y Task 6.)
3. **Perfil incompleto:** coordinador sin `area` o sin `sede_id` → `puede_ver_usuario` devuelve `false` para todos menos él mismo (no ve "todo" por un null). (Test en Task 3.)
4. **Invitar un email que ya existe:** la acción devuelve el error "Ya existe un usuario con ese email" y no duplica el perfil. (Test en Task 7.)
5. **Líder de un equipo de otra sede o un equipo sin líder:** `puede_ver_usuario` no debe filtrar usuarios por un `lider_id` null. (Test en Task 3.)
